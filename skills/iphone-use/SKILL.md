# Completar tareas del iPhone con PUA

Si la conversación nueva no tiene una prueba READY válida de esta conversación, ejecuta primero el flujo de inicialización de abajo y solo después empieza la tarea en el teléfono. Que un chat anterior haya tenido éxito, que el plugin esté instalado, que el widget esté abierto o que se vea el icono de Runner no sustituyen el READY de esta conversación. Que el servicio PUA aún no esté arrancado es un paso de arranque que hay que seguir tratando; no termina antes de tiempo la tarea del usuario. La configuración existente se reutiliza por defecto: solo se arranca el servicio que falte y no se reinstala todo el conjunto.

Determina primero el resultado que el usuario quiere entregar y la condición de terminación. Por defecto, trata una acción que vuelve con normalidad como ejecutada según el plan y prepara el paso siguiente. No llames a una observación solo para demostrar el éxito de cada toque, cada cambio de página, Home, cada arranque o cada escritura. Cuando el paso siguiente necesite información de la página, léela una vez y juzga de paso si el paso anterior surtió efecto; ajusta o repite solo si está claro que no. La operación final crítica, el resultado de enviar o entregar, el texto crítico y el archivo entregado necesitan evidencia del resultado real.

El `ok`, `verified` y `complete` de la herramienta, y el completed del host, solo describen la llamada correspondiente; no significan que toda la tarea haya terminado. `action_complete` indica que ese comando ya se procesó, no que el resultado de negocio esté aceptado. Un `verified=false` en una vuelta normal significa que no hubo una comprobación aparte; no es un fallo y no obliga a detenerse. Sigue el camino conocido hasta que se cumplan todas las condiciones de terminación, se haya contrastado el resultado crítico y se haya completado la entrega. No termines antes con un «a continuación leeré…». En una tarea larga, da un avance breve de forma continua.

## READY y autenticación

En una tarea normal, la primera vez que esta conversación usa el teléfono, llama directamente a `pua_setup(action="status")` y, según [arranque y recuperación](references/startup.md), reutiliza un servicio sano o un trabajo activo; haz start una sola vez solo si falta el servicio. Cuando el servicio esté listo, llama a `pua_ready(recover=true, screenshot=false)`. No esperes a que READY falle para hacer setup. Una tarea de texto conserva la comprobación de status / session / tree / viewport / desbloqueo, sin captura adicional. Si esta conversación ya tiene READY y el canal no ha caducado, reutilízalo directamente y no lo vuelvas a comprobar en cada paso. `recover=false` solo sirve cuando el usuario prohíbe reiniciar o pide con claridad un diagnóstico de solo lectura; no lo actives por precaución ni anules con él una restricción del usuario.

- `ready=true, state="ready"`: el canal ya se puede usar. Reutiliza directamente la `observation` de READY para preparar el paso siguiente. No repitas observe de inmediato ni añadas otra ronda de doctor, observación o prechequeo de navegación.
- `ready=false, state="recovering"` o `state="recovery_required"`: no hay error y MCP isError=false, pero aun así no significa que el teléfono se pueda operar. Consulta el mismo trabajo o respeta la restricción del usuario según [arranque y recuperación](references/startup.md).
- READY devuelve `pua_unreachable`, conexión rechazada, `not_ready` o deja claro que el servicio no está arrancado: es la rama de arranque, no el fracaso de toda la tarea. `recover=true` no hace un arranque en frío por su cuenta. Llama a `pua_setup(action="status")`, reutiliza el trabajo start / recover que esté activo o, si ya está configurado y no hay trabajo activo, haz start una vez; cuando el servicio esté listo, vuelve a comprobar READY. El procedimiento paso a paso está en [arranque y recuperación](references/startup.md). Si faltan configuración / código fuente / compilación, lee `iphone-use-setup`.

Las restricciones del usuario, como solo lectura o prohibir arrancar / reiniciar, se conservan siempre. Después de recuperar, reutiliza la observación nueva de READY para ver el avance de la tarea original; no reejecutes una acción de negocio que quizá ya surtió efecto.

READY queda asociado a la barra lateral de la pantalla del teléfono. Si el host lo admite, la abre por defecto o reutiliza el panel que este chat ya tenga. Repetir setup / recuperar el canal, y pausar / reanudar la vista previa, siguen el mismo widget. Si el panel ya existe, continúa directamente y no llames otra vez a la herramienta de abrir pantalla solo para refrescar. Para volver a abrir un panel que se cerró, llama una vez a `pua_screen()`; no repitas READY para abrir la imagen. Si el usuario pide «abre primero el widget para que lo vea», ábrelo primero y continúa con la inicialización y la tarea ya autorizada. Espera solo si pide con claridad que esperes su confirmación antes de operar. Arriba, el widget muestra el modelo y el estado En vivo; los tres botones de abajo —actualizar, pantalla de inicio y captura— los pulsa el usuario y no son herramientas del modelo. No llames a `pua_screen_frame` ni a `pua_screen_action`, que son solo para la app, y no añadas sondeo, captura u observe para refrescar la vista previa. Después de que el usuario pulse la pantalla de inicio, la página cambia; continúa según el estado real observado una vez. Una imagen en blanco, el efecto de luz o el cursor no demuestran READY, el éxito de una acción ni que la tarea haya terminado, y no son la observación del modelo. Un problema de vista previa se diagnostica según [canal de pantalla](references/screen.md); no recuperes el canal de control una y otra vez por eso.

Cuando la app pide de verdad contraseña, PIN, código de verificación o Face ID / Touch ID, o el teléfono necesita que el usuario lo desbloquee, espera a que el usuario termine según [toma de control por autenticación y recuperación](references/authentication.md). La autenticación de la app empieza con `pua_screen(action="pause")`. `phone_locked` ya queda en pausa automática como `device_locked`; no lo tapes con otro pause explícito. Hay que llamar a la herramienta de pregunta del host (en Default, de preferencia `functions.request_user_input_async`). La primera opción es siempre «Listo, continuar»; la segunda puede ser «No puedo terminar por ahora». Una vuelta asíncrona o una preselección no son la respuesta del usuario. Durante la toma de control, pausa las acciones, las lecturas y las capturas del teléfono, y no pidas credenciales. Tras el aviso real de que terminó, una autenticación de app o una pausa unknown de una versión anterior hacen primero `pua_screen(action="resume")` y después toman una observación nueva. El desbloqueo del dispositivo vuelve a comprobar READY y, si tiene éxito, levanta solo la pausa de ese mismo bloqueo. `preview.paused` / `pause_reason` de READY explican el estado de la vista previa. No tomes un READY correcto como que la autenticación de la app ya terminó. Continúa el trabajo que quede según el estado nuevo.

## Elegir la observación según el paso siguiente

Un objetivo semántico único y conocido, y un camino de navegación conocido, usan el `observe="none"` por defecto; se pueden ejecutar seguidos o reunir en un batch. Cuando el paso siguiente tenga que reconocer una página desconocida, elegir una zona o leer contenido, pon en esta misma acción `observe="tree" / "screenshot" / "both"` y usa la `observation` anidada que vuelve para planear el paso siguiente y juzgar de paso la acción anterior. No uses primero none y después un observe aparte como verificación, porque eso añade un turno del modelo. Una lectura independiente usa `pua_observe(mode=...)`; no mezcles mode y observe.

Cada nodo del árbol conserva un solo dato de cada hecho: `type` no lleva el prefijo `XCUIElementType`; `rect` es `[x, y, width, height]` (puntos del iPhone). Que no haya `name` significa que es igual a `label`; que no haya `value` significa que es igual al texto; que no haya `enabled` / `visible` / `in_viewport` significa true. Mantén `include_invisible=false`, `max_nodes=100` y `expensive_visibility=false`. Para buscar un solo objetivo usa `pua_find` / `pua_wait`; no vuelvas a pedir el árbol entero. Que el árbol esté truncado, o que el nodo esté dentro del viewport, no demuestra que el contenido sea completo ni que el objetivo no esté tapado: una cabecera fija o una capa flotante pueden cubrirlo.

Toma una captura solo cuando el contenido dibujado por la app, una oclusión o una etiqueta ausente exijan un juicio visual. La captura vuelve como imagen en el mismo resultado y ya está escalada a un tamaño legible: multiplica los píxeles de la imagen por `[x, y]` de `image.pixel_to_point` para obtener puntos del iPhone; no conviertas según la resolución original ni según la pantalla del Mac. screenshot se salta el XML; both aporta a la vez el árbol y la imagen. Si la app muestra una capa flotante de compartir, trata el estado actual y no repitas en bucle la captura del mismo camino.

## Si la interfaz falla, mira primero la captura

La captura es el recurso general cuando la interfaz se comporta mal. Si fallan el selector o el foco, si después de desplazar sigue sin haber un objetivo pulsable, si el desplazamiento no avanza, si una zona está tapada o el contexto cambió, si la relectura de lo escrito no coincide o si no aparece la página esperada, mira primero la captura actual que trae el resultado y decide entonces la operación siguiente. Si no hay una captura utilizable, toma una vez `pua_observe(mode="screenshot")`. No releas antes el árbol entero, no cambies la forma de la etiqueta, no aumentes el número de desplazamientos ni reintentes igual. También sigue este flujo si el árbol está truncado, si un toque por coordenadas no surtió efecto de forma evidente o si la página no coincide con lo esperado. Un `verified=false` ordinario sigue sin ser una anomalía y no exige una captura en cada paso.

La captura sirve primero para juzgar la página actual, si se movieron la primera y la última fila, el control o el blanco del final, un diálogo / una cabecera fija y la zona que de verdad se puede desplazar. Detén la búsqueda cuando ya se vea el objetivo o el límite del alcance de la tarea. Si la imagen ya no se mueve, trata primero el límite o la oclusión y decide después si hace falta otra zona u otra dirección. `direction` es siempre la dirección del movimiento del dedo; up suele mostrar el contenido de más abajo. La vista previa en vivo de la barra lateral del usuario no sustituye que el modelo mire de verdad la imagen de la herramienta.

- Toque: `tap_point` y el `tap` de candidates son la posición del elemento (puntos del iPhone) y no demuestran que se pueda pulsar. Un cupón, un anuncio, un menú o una capa flotante de inicio de sesión pueden cubrir un control del fondo. Encuentra primero en la captura el botón visible de cerrar o cancelar, trata la oclusión y después toca el objetivo.
- Escritura: toca primero el campo de texto que se vea de verdad en la captura y llama después a `pua_type_text(text=...)` sin selector. `no_focused_field` significa que no hubo escritura. El toque anterior pudo interceptarlo una capa flotante o caer en el sitio equivocado; no repitas igual ese grupo de coordenadas y esa escritura. Elige otro punto según la captura actual y, si el paso siguiente necesita información, haz que la acción devuelva la captura para juzgar la página y el foco.
- El objetivo está fuera de la pantalla: desliza primero hacia el objetivo y toca según la captura posterior. Si falla la espera de una etiqueta o la búsqueda por desplazamiento, continúa según la imagen real y no repitas en bucle la misma etiqueta.

El punto de píxel de la captura `(px, py)` se convierte en `x=px*image.pixel_to_point[0]` y `y=py*image.pixel_to_point[1]` y se pasa a `pua_tap`. x/y aceptan puntos del iPhone; no pases directamente píxeles de la captura ni coordenadas del widget del Mac.

Al llamar a la herramienta mediante `functions.exec`, hay que reenviar de verdad la imagen al modelo; no saques con `text(result)` el resultado entero, que incluye base64:

```javascript
const result = await tools.mcp__iphone_use__pua_observe({mode: "screenshot"});
for (const block of result.content ?? []) {
  if (block.type === "text") text(block.text);
  else if (block.type === "image") image(block);
}
```

Un resultado fallido de toque, escritura u otra acción también reenvía el bloque de imagen. Si la imagen no se reenvió, abre con `view_image` el `image.path` / `error.observation.image.path` devuelto. No trates los metadatos de la imagen o el base64 como si hubieras visto la captura.

Lo anterior sirve para un problema recuperable de localización en la interfaz. Un error de parámetros se corrige según el schema, un fallo del canal recupera READY, y la pantalla bloqueada o la autenticación las completa el usuario. Si no está claro si la acción surtió efecto, lee primero el estado real; no reejecutes una escritura, un envío, un pedido o el lote entero. Una oclusión habitual que la captura baste para tratar debe seguir intentándose; no devuelvas la tarea al usuario antes de tiempo.

## Apps y acciones habituales

Cuando haya que traer al Mac imágenes, vídeos u otros archivos del teléfono para usarlos, sigue [devolver archivos al Mac con AirDrop](references/airdrop.md): después de enviarlos, basta con encontrar el archivo en el directorio de descargas.

Un bundle ID conocido y verificado se puede lanzar directamente. Para consultar sin red una app habitual, usa `pua_apps(source="catalog", query=...)` o el [directorio de apps habituales](references/apps.md). Una app desconocida o con el mismo nombre usa `source="auto"` para ver los candidatos de este teléfono, y solo si sigue sin haber resultado consulta Apple. No adivines ID uno tras otro. La app principal 招商银行 es `com.cmbchina.MPBBank`. Un registro de tienda o del directorio no demuestra la instalación en este teléfono; `installed_verified=true` es la evidencia de instalación. La observación que prepara el paso siguiente después del arranque muestra a la vez el primer plano real, sin añadir una comprobación de primer plano por defecto.

- `pua_launch_app`: después de activar una vez, continúa. Por defecto `verify=false, observe="none"`. Pon observe cuando el paso siguiente necesite información de la página nueva. Cuando una entrada crítica tenga que demostrar la app / la página de destino, usa `verify=true` explícito o pasa `expect`.
- `pua_tap`: usa de preferencia `selector` y copia tal cual, desde el nodo actual, label / name / value / type; se puede añadir enabled. Si la etiqueta es muy larga o contiene una hora o una cifra que cambian, usa `label_contains`. predicate se usa solo y conserva el salto de línea, las comillas y la barra invertida de la etiqueta real. rect, visible e in_viewport no son campos del selector. Si las coincidencias del mismo nombre están apiladas en el mismo sitio (por ejemplo, una Cell y el texto que contiene), o solo una está en pantalla, la herramienta toma ese objetivo y lo explica en `target` del resultado. Varias coincidencias separadas devuelven `ambiguous_target` y candidates con `index`, tipo, posición, coordenadas `tap` y `hittable`; toca según las coordenadas `tap` del objetivo (o usa el mismo selector más `index`). No elijas la primera al azar y no hace falta observar otra vez por eso. Si el selector falla o la semántica no basta, usa coordenadas x/y en puntos del iPhone. observation_id es opcional; si se aporta, tiene que venir del mismo Runtime y solo contrasta el contexto de app / viewport. Si la información de la página ya basta para localizar, no leas de más el árbol ni la captura. Después de cambiar de página, de una toma de control del usuario o de una rotación, vuelve a localizar según la información actual.
- `pua_press_button`: usa solo los botones que admite el schema. Home usa el camino dedicado homescreen; por defecto `verify=false`, y una vuelta normal basta para preparar el paso siguiente. Cuando haga falta con claridad el estado de la pantalla de inicio, usa `verify=true` explícito. Si el enlace MCP no está disponible, continúa la misma acción ya autorizada según [fallo de herramientas y llamada por código](references/tool-fallback.md).
- `pua_swipe`: la dirección es la del movimiento del dedo; up suele recorrer el contenido posterior. Por defecto `verify=false, observe="none"`: ejecuta el gesto una sola vez y no lee XML para comprobar el avance. Se puede pasar region según una lista conocida, sin forzar observation_id ni tree. Cuando el paso siguiente lea el contenido de la lista, juzga de paso si se movió. Si está claro que no se movió, mira primero en la captura la entrada, el límite, la capa flotante o la zona. `verify=true` explícito comprueba una sola vez el cambio geométrico del gesto. Si no hay avance o cambia el contexto, adjunta la captura y la devuelve al modelo; aunque se pase el parámetro antiguo `max_attempts=2`, no cambia de gesto ni reintenta por su cuenta.
- `pua_wait`: úsalo con un timeout acotado solo cuando de verdad se dependa de que aparezca un control. No hace falta un sleep largo fijo, ni añadir un wait a toda la navegación. `pua_scroll_find`: si el objetivo ya se puede pulsar, vuelve directamente; ante oclusión o ambigüedad, se detiene de inmediato y adjunta la captura. Una llamada se desliza como máximo una vez. Si después de desplazar sigue sin haber un objetivo pulsable, mira primero la captura devuelta y juzga entonces si sigues deslizando. `max_swipes=0` solo busca; un número positivo, aunque sea mayor que 1, no se desliza a ciegas en serie. Cuando lo encuentre, continúa el paso siguiente y no repite la búsqueda del mismo resultado.

`expect` y `verify=true` son opciones de comprobación explícita, para un estado final crítico o una dependencia real, no un campo obligatorio de cada paso. HTTP accepted y el éxito de negocio son hechos distintos. Una tarea habitual continúa con optimismo, y la conclusión final se apoya solo en el resultado crítico. Ante un error claro, una escritura / un envío uncertain o una acción completada solo en parte, mira primero el estado real y decide después los pasos que quedan.

## Escritura y envío

Da de una vez, con `pua_type_text(selector, text)`, el contenido completo que el usuario necesita. No escribas antes un texto corto de prueba ni ASCII, ni partas el texto por tu cuenta. Si el selector no encuentra el campo, no reintentes con otra grafía: toca el campo por coordenadas y llama después a `pua_type_text(text=...)` sin selector para escribir en el foco actual. Por defecto `replace=true, allow_newlines=false, submit=false, verify=false, observe="none"`. Después de una búsqueda, un filtro u otra escritura ordinarios se puede seguir con el paso siguiente; si la página siguiente es desconocida, esta misma acción devuelve la observación y se juzga de paso. Cuando haya que conservar un borrador ya existente, decide según el contenido actual si se reemplaza o se añade. El texto final crítico puede contrastar el campo completo con `verify=true` explícito. La contraseña, el código de desbloqueo del teléfono y el código de verificación los escribe el usuario.

El texto largo lo parte la herramienta al escribirlo. Si el resultado es `input_complete=false`, el texto aún no se ha terminado de escribir: llama otra vez a `pua_type_text` llevando solo el `continue_token` devuelto, sin reenviar el texto ni adjuntar otros parámetros, y mientras tanto no toques, no deslices ni cambies de página. verify / submit / expect / observe de la llamada original se ejecutan solo cuando todo se ha escrito. Si la continuación caduca (`input_continuation_expired`), no se escribe nada: lee primero el texto real del campo y, con `replace=false`, completa solo la parte que falta. Un error a mitad de la escritura trae `characters_confirmed`; igual que antes, relee primero y no vuelvas a escribir el tramo entero.

El contenido multilínea puede disparar un envío con Return dentro de un control de chat. Pon `allow_newlines=true` solo cuando sepas con certeza que el TextView actual es un editor multilínea adecuado. No cambies a escondidas a una sola línea el formato que pidió el usuario. Permitir el salto de línea no autoriza el envío. Cuando el usuario ya haya autorizado enviar, contrasta la conversación de destino y el borrador completo en una observación previa al envío o en una comprobación explícita de la escritura, y envía una sola vez. Después del envío, contrasta el contenido final y el número de envíos. `submit=true` no demuestra el resultado del envío; después de enviar, se acepta con la página o el registro reales del resultado. Completa el envío solo si está claro que no se envió. No reenvíes por un timeout, por no haber verificado por separado o por un `verified=false` ordinario.

Los textos chinos entrecomillados son etiquetas literales de interfaces configuradas en chino. Cuando la locale del dispositivo o de la app sea distinta, usa siempre la etiqueta visible o el equivalente que muestre esa interfaz, sin adivinar selectores.

En la medida de lo posible, ordena un mensaje de chat de 微信 en un solo texto sin saltos de línea, escríbelo y envíalo de una vez, para que el cuadro de chat no interprete el retorno como envío. Cuando de verdad haga falta un diseño en varias líneas, no entregues a `pua_type_text` el tramo entero que contiene `\n`. Escribe primero el contenido como borrador y confirma que el foco está en el campo de 微信; toca una zona en blanco dentro del campo para sacar la toolbar de edición de texto y pulsa «换行» en esa toolbar para insertar el salto. Repítelo según haga falta, contrasta el borrador completo y, al terminar, pulsa una sola vez «发送». Si la toolbar no aparece o no tiene la opción «换行», detente y vuelve a localizar según la interfaz actual; no sustituyas eso por el Return del teclado. Esta operación depende de la versión actual de 微信 y de la toolbar que el campo muestre de verdad. No infieras que el salto se insertó de forma segura solo porque `allow_newlines=true`.

## Ejecución continua y recolección de listas

Reúne con `pua_batch` un camino corto conocido, de 20 pasos como máximo. Un tap, un launch, Home, una escritura y un desplazamiento habituales no necesitan expect, y un `verified=false` ordinario no corta los pasos posteriores. Se puede dejar un observe al final del plan, u observar solo en la posición cuyo paso siguiente necesite información. Un error claro, una acción incierta o un submit no comprobado detienen el lote. También se detiene si el texto largo no se terminó de escribir (`stop_reason="input_continues"`) o si se alcanza el presupuesto de tiempo de una llamada (`"time_budget"`). Continúa los pasos que queden según completed_steps / stopped_at y el resultado de cada paso; no reejecutes el lote entero. Vuelve a partir el trabajo cuando una página desconocida, la autenticación o un diálogo dinámico necesiten información nueva, y no mezcles en la navegación un envío no autorizado.

Al buscar un registro cuya posición se desconoce, no metas de antemano en el batch varios swipe en la misma dirección. Desliza un paso y lee la página que el paso siguiente necesite. Si el árbol truncado no deja ver el final, o la página no avanza, toma una captura y juzga entonces si continúas. Un camino corto conocido se puede seguir reuniendo. Deja de desplazar cuando aparezcan el alcance de la tarea o el final de la lista.

`pua_collect_list(row_type="Cell", max_pages=6)` recolecta con un límite de 10 páginas como máximo, se desliza una sola vez cada vez y recolecta directamente la página nueva; reutiliza el árbol completo y el viewport. Juzga una página repetida por la fila de destino: no descarta una página nueva porque una lista virtualizada haya cambiado todas las etiquetas, ni prueba de más un gesto de reserva. Devuelve rows, pages y stop_reason, y complete es siempre false. Deduplica el mismo type/name/label/value, así que registros que se muestran igual pueden quedar plegados. Se puede pasar end_selector como evidencia de cobertura. Al final, contrasta según lo que pidió el usuario el alcance, el número de entradas, el total, las fechas y los campos que faltan. Alcanzar el límite o no avanzar no permite afirmar que ya está el conjunto completo. Si los campos del detalle no bastan, entra en el detalle y léelos; no exijas una verificación aparte cada vez que se entra en un detalle. La comprobación crítica concreta está en [comprobación de recolección y escritura](references/verification.md).

## Ajustar ante una anomalía clara

`occluded_target` falla antes del click: no se envió el toque, y tampoco se puede inferir que un toque fallido haya abierto una capa flotante. Mira la captura adjunta al error. Si el objetivo se ve, tócalo por coordenadas según `tap_point`. Si de verdad hay una capa flotante, un selector o una cabecera fija que lo cubren, trátalos primero (la entrada real de cierre, o un punto fuera del panel que se pueda cerrar sin riesgo) y continúa. `offscreen_target` mete primero el objetivo en la pantalla. Un panel a media pantalla personalizado puede no tener nodos nativos Alert / Sheet; manda la captura, y no concluyas que no hay oclusión solo porque el árbol del fondo todavía tenga botones.

`no_scroll_progress`, devuelto por una verificación explícita de desplazamiento, solo indica que el gesto se ejecutó y no se demostró que la lista se moviera; no demuestra una lista vacía ni que se haya llegado al final. Esa anomalía, `scroll_context_changed` y una zona bloqueada por una capa flotante adjuntan captura aunque se haya pedido `observe="none" / "tree"`. Si el resultado ya trae captura, reutilízala. Si la recolección de la lista se detiene por una página repetida, también adjunta captura y conserva las filas ya recolectadas y el límite de cobertura. Mira primero la imagen y trata después el límite, la capa flotante o la zona; no aumentes el número de veces a ciegas. Un gesto ordinario sigue sin leer el árbol de más solo para verificar.

`action_executed=true, action_complete=false` o `uncertain=true` indican que la acción, o parte de los pasos, pueden haber surtido efecto. Una escritura, un envío, un pago, un pedido y acciones parecidas leen primero el contenido / el registro reales; no se puede reejecutar la operación entera. Un fallo breve de una consulta pura lo puede releer la herramienta con un límite, y eso no equivale a haber ejecutado una acción en el teléfono. `local.pid.0`, `pua_foreground_unavailable` o XCTest Code 41 son fallos del canal: recupera según la guía de READY y continúa la tarea que quede reutilizando la observación nueva. Recuperar el servicio no reejecuta la acción de negocio.

Si falla el enlace de la herramienta, se puede usar el punto de entrada de código del plugin, reutilizando la misma configuración, sesión y cerrojo de operación. No abandones porque MCP no esté disponible ni abras en paralelo otra sesión de control. `pua_metrics` da el tiempo HTTP y de las herramientas, los bytes que devuelve cada herramienta y la espera entre dos llamadas (la suma del tiempo del host, del modelo y del usuario). El resultado de una optimización se mide por el tiempo real de la tarea y por lo completa que sea la entrega; no digas que el negocio quedó demostrado solo porque se omitió la comprobación de cada paso.
