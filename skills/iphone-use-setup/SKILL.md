# Dejar el iPhone en READY

Usa las herramientas MCP de este plugin para completar un sondeo, una compilación, un arranque y una conexión que se puedan repetir. No generes un cliente Python improvisado en cada tarea. Si ya hay un PUA utilizable, reutilízalo primero y evita recompilar o reinstalar en cada tarea.

## Determinar primero el estado actual

La primera vez que esta conversación usa el teléfono y aún no hay READY, llama directamente a `pua_setup(action="status")`. Según la sección siguiente, reutiliza un servicio sano o un trabajo activo, y haz start una sola vez solo si falta el servicio. Cuando el servicio esté listo, llama a `pua_ready(recover=true, screenshot=false)` y ejecuta entonces la tarea del usuario en el teléfono. No falles primero READY y después hagas setup. No sustituyas la prueba actual por un READY de un chat anterior ni por un plugin ya instalado. Si esta conversación ya está READY y el canal no ha caducado, continúa directamente; no repitas doctor, discover, build y start para cada tarea. En la primera configuración, o cuando READY devuelva lo que falta en concreto, usa `pua_doctor` y `pua_setup(action="discover")` para leer Xcode, el dispositivo conectado, la firma, el puerto y el estado de los procesos. Si hay varios iPhone, elige según el dispositivo que indique el usuario; si solo uno cumple las condiciones, se puede usar directamente. El UDID del dispositivo, el Team ID, el registro y la configuración de firma se guardan en el equipo del usuario y no se escriben en el código fuente ni en Git.

Una tarea normal llama a `pua_ready(recover=true)`, o omite recover y usa el true por defecto; no desactiva la recuperación por un prechequeo o por precaución. Pasa `recover=false` solo en un diagnóstico de solo lectura o cuando el usuario prohíba reiniciar con claridad, y conserva la restricción. Cuando una tarea habitual no necesite captura, se puede pasar `screenshot=false`; la capacidad de captura se usa cuando de verdad haga falta una captura. La prueba que devuelve `ready=true, state="ready"` incluye el status de PUA, una sesión utilizable, la app real en primer plano, el viewport del dispositivo, el estado de desbloqueo y la observación actual. Prepara el paso siguiente directamente con la observation anidada; no repitas observe de inmediato ni hagas otra ronda de prueba de navegación. Si la duplicación de pantalla está ocupada y el árbol de elementos está vacío, la herramienta devuelve `mirroring_conflict`: sal de la duplicación y vuelve a comprobar READY. El icono de Runner, BUILD SUCCEEDED o un puerto abierto no bastan para declarar READY. READY también queda asociado a la barra lateral de la pantalla del teléfono y, si el host lo admite, la abre por defecto. Para volver a abrir la imagen cuando el canal ya existe, usa `pua_screen()`; no repitas READY. La vista previa va por un canal USB MJPEG independiente (puerto de dispositivo 9100 por defecto) y no usa sondeo de XML ni de capturas. Que la vista previa no esté disponible no niega por sí solo el READY del canal de control, ni exige un bucle de reinicios. READY demuestra que el canal de control se puede usar. Una operación habitual de app se ejecuta con optimismo por defecto; la observación que el paso siguiente necesite juzga el avance de paso, y solo el resultado final crítico se comprueba de forma explícita.

`phone_locked` pausa sola la vista previa y registra `device_locked`; no hace falta otro pause explícito. Espera el aviso real de que el usuario desbloqueó y vuelve a comprobar READY. Si tiene éxito, levanta solo la pausa de ese mismo bloqueo; la autenticación de la app y una pausa unknown de una versión anterior siguen exigiendo una reanudación explícita. El `preview` de READY devuelve el motivo de la pausa. No tomes una vista previa en blanco como un fallo del canal de control.

## Seguir la inicialización si el servicio no está arrancado

`recover=true` puede encolar la recuperación de un servicio cuya pertenencia ya se verificó ante un fallo persistente de `local.pid.0` / XCTest. No significa que complete solo la primera configuración o el arranque en frío. Un resultado de no arranque de READY, como `pua_unreachable`, conexión rechazada o `not_ready`, debe entrar en la rama de arranque de abajo; no se puede declarar en el final que la tarea del teléfono ha fallado:

1. Llama a `pua_setup(action="status")`. Si devuelve `configured=true`, conserva el dispositivo, la firma y los puertos actuales. Solo con `configured=false` se completa, según la sección de la primera instalación, lo que falte de verdad.
2. Revisa el array `jobs` devuelto. Si ya hay un trabajo start / recover, en queued o running, que corresponde a la configuración / endpoint actuales, consulta ese mismo trabajo por su `id`; no repitas start ni esperes un trabajo antiguo que no corresponda. Si hay un trabajo fetch / build correspondiente en marcha, reutilízalo primero. `pua_setup(action="status", job_id=...)` sigue devolviendo un array `jobs`; no supongas que devuelve un solo job.
3. `service.ready=true` significa que el servicio se puede sondear; aun así hay que volver a comprobar READY para verificar la session, el primer plano, el viewport y el resto del canal completo. Si el trabajo start sigue en running y el servicio está disponible, ya se puede comprobar READY. Un trabajo recover se comprueba con READY cuando llega a `recovery_phase="serving"`; el Runner de larga duración no espera succeeded.
4. Si ya está configurado, el servicio no está en marcha y no hay un trabajo activo correspondiente, llama una vez a `pua_setup(action="start")` y reutiliza la compilación válida. start espera con un límite de 20 segundos como máximo y vuelve antes si el servicio queda listo o el trabajo termina; no es un sleep fijo. Si devuelve `service.ready=true`, pasa directo a READY sin volver a consultar status. Si aún no está listo, espera el mismo trabajo con `pua_setup(action="status", job_id=..., wait_seconds=20)`. El tiempo agotado solo significa que sigue arrancando; no se puede hacer start otra vez. Anota el `job_id` que devuelve el trabajo nuevo. Cuando `already_running=true`, anota `job.id` y, si hay que esperar, consulta el mismo trabajo con `pua_setup(action="status", job_id=..., wait_seconds=20)`. Si start informa con claridad de que falta el código fuente, haz fetch; si informa con claridad de que falta una compilación válida, de que la firma caducó o de que el binario es incompatible, haz build y continúa con start. No reinstales ni vuelvas a firmar por completo solo por un arranque en frío. Si el trabajo falla, mira el registro exacto de ese trabajo y next_steps, y trata entonces lo que falte de verdad; no entres en un bucle de start.
5. Cuando obtengas `ready=true`, reutiliza la observation actual y continúa la tarea original. Solo un bloqueo real de USB / Xcode / firma / permiso necesita el tratamiento correspondiente. Cuando tenga que ser el propio usuario quien desbloquee, confíe, inicie sesión o confirme, usa el flujo de pregunta del host cuya primera opción es «Listo, continuar». Si el usuario pide con claridad solo lectura o prohíbe arrancar / reiniciar, conserva la restricción y no la rodees con la inicialización.

Si este chat ya tiene el widget, volver a ejecutar setup, arrancar / recuperar el canal y comprobar READY otra vez reutilizan el panel existente; no llames de más a `pua_screen()` para abrir una pestaña nueva. Si el usuario solo pide «abre primero el widget para que lo vea» y el panel aún no está abierto, llama a `pua_screen()` para abrir la vista previa y continúa con la inicialización y la tarea ya autorizada, sin añadir un control que espere aprobación. Si el usuario pide con claridad esperar primero su confirmación, hazlo. Una vista previa en blanco mientras no ha arrancado no demuestra READY ni significa que toda la tarea haya fallado.

## Primera instalación

Los textos chinos entrecomillados son etiquetas literales de interfaces configuradas en chino. Cuando la locale del dispositivo o de la app sea distinta, usa siempre la etiqueta visible o el equivalente que muestre esa interfaz, sin adivinar selectores.

1. Según lo que doctor indique que falta, guía al usuario para preparar un Xcode completo que coincida con iOS, aceptar el permiso del primer arranque e iniciar sesión con su Apple Account en los ajustes de cuenta de Xcode. El inicio de sesión de la cuenta, la contraseña, el código de verificación y el desbloqueo del dispositivo los completa el usuario en la interfaz del sistema; no pidas credenciales.
2. Conecta el iPhone con el cable. En el primer emparejamiento, el usuario toca «信任此电脑» en el teléfono. Confirma que el dispositivo ha sido reconocido desde Devices and Simulators de Xcode o desde lo que devuelve discover. Que solo se vea en Finder no significa que el emparejamiento de desarrollo haya terminado.
3. Según el aviso real del sistema, activa «设置 → 隐私与安全性 → 开发者模式» y completa la confirmación después de reiniciar. Si esa entrada no existe, deja primero que Xcode termine el emparejamiento y la preparación de desarrollo del dispositivo, y vuelve a comprobar. No interpretes que falte la entrada como que no se admite de forma permanente. Si hace falta, revisa «设置 → 开发者 → 启用 UI 自动化».
4. Obtén con `pua_setup(action="fetch")` el servicio de ejecución en el teléfono, de versión fija, que usa PUA. Después, `configure` configura el `udid`, el `team_id` y el `bundle_id` que se pueda firmar del usuario. Son opcionales `source_dir`, `local_port` y `device_port`; por defecto, el reenvío local usa el puerto 18100 y el puerto del dispositivo es 8100. Los datos de ejecución local están por defecto en `~/.local/share/iphone-use`. No copies el UDID, el Team ID ni la firma del autor. Si la firma automática falla, mira el registro devuelto y, en Signing & Capabilities del target Runner, elige el Team del propio usuario. Ajusta el bundle ID o el provisioning solo si el error lo exige.
5. Compila con `build` y después, con `start`, instala e inicia el servicio de prueba del Runner y el reenvío USB local. fetch/build/start son trabajos en segundo plano. Anota job_id, consulta el trabajo existente con `pua_setup(action="status", job_id=...)`, encuéntralo por id en el array `jobs` devuelto y no supongas que status devuelve un solo job. fetch / build se miran en su estado final y, si fallan, se lee el registro exacto. start es un Runner de larga duración: si el trabajo sigue en running y `service.ready=true`, ya se puede llamar a READY, sin esperar succeeded y sin repetir start. Consulta según el estado, el registro y retry_after_seconds devuelto; no esperes a ciegas con un intervalo largo fijo ni un número fijo de veces. start usa la compilación correcta de la configuración actual. Mantén el iPhone conectado por USB y disponible para las pruebas de interfaz.
6. Si el teléfono o Xcode informan de que el desarrollador no es de confianza, completa la verificación según «设置 → 通用 → VPN 与设备管理» de ese dispositivo y su entrada de desarrollador. Manda el aviso actual; no apliques a toda firma de desarrollo el flujo de una app de empresa. Después ejecuta `status` y `pua_ready`.

Si el usuario debe iniciar sesión en su cuenta, introducir una contraseña, desbloquear el dispositivo, confirmar una acción en el teléfono o instalar Xcode, explica qué pantalla debe atender, por qué hace falta y qué paso permitirá continuar. Llama a la herramienta de preguntas disponible en el host (en Default, de preferencia `functions.request_user_input_async`). La primera opción es siempre «Listo, continuar»; la segunda puede ser «No puedo terminar por ahora». Una vuelta asíncrona, una preselección o que haya pasado un rato no significan que el usuario haya terminado. Continúa la configuración que depende de ese paso solo cuando el usuario elija de verdad «Listo, continuar» o responda con claridad que terminó. Solo si el host no tiene capacidad de pregunta, espera con una explicación en texto. El resto de la configuración independiente puede seguir ejecutándose. No añadas un control de confirmación único para una instalación local ya autorizada. No borres apps de desarrollo que el usuario ya tenga, no revoques un certificado compartido ni subas la cuenta de pago para rodear un error.

## Comprobación de READY y recuperación

READY ya devolvió el dispositivo, la sesión, el viewport y la observation actual; reutiliza esa información para preparar el paso siguiente. No releas el árbol a continuación ni añadas un prechequeo de navegación a cada tarea. Prueba en una página sin efectos secundarios solo cuando un diagnóstico concreto lo necesite de verdad. La navegación habitual usa por defecto observe=none y verify=false. Cuando el paso siguiente necesite información de una página desconocida, esta misma acción devuelve tree / screenshot / both, sin añadir otra ronda de verificación. La operación final crítica usa expect / verify explícitos o una lectura del estado final.

Después de que el canal esté READY, la app de destino aún puede pedir contraseña, código de verificación o Face ID. Según [toma de control por autenticación y recuperación](../iphone-use/references/authentication.md), llama primero a `pua_screen(action="pause")` para detener la vista previa y vaciar la imagen, y después llama a la herramienta de pregunta como indica esa referencia para que el usuario lo complete en el iPhone; la primera opción es «Listo, continuar». Durante la toma de control, pausa las llamadas al teléfono. Cuando el usuario elija de verdad «Listo, continuar», o llegue un aviso claro de que terminó, llama a `pua_screen(action="resume")` y vuelve a observar la app y la página de destino. La autenticación de la app no es un fallo de PUA; no repitas build / start / recover por eso. Recupera READY solo cuando el teléfono esté de verdad bloqueado o el canal se interrumpa.

Después de una desconexión, un reinicio, detener el proceso de prueba o salir del reenvío USB, consulta status según el flujo de no arranque de arriba y reutiliza el trabajo / la compilación existentes. Llama a doctor solo cuando lo que falte en concreto lo exija; recupera la conexión o haz start según la capa que falte y, al final, vuelve a comprobar READY. Después de que el usuario tome el control del teléfono, vuelve a observar la app actual; no sigas usando las coordenadas anteriores a la toma de control ni adivines la página original.

`XCTDaemonErrorDomain Code=41`, `local.pid.0` o `pua_foreground_unavailable` son fallos del canal PUA / XCTest. No se resuelven cambiando el selector ni tratando `status.ready=true` como prueba de que se puede operar: llama a `pua_ready(screenshot=false)`. Primero reconstruye la sesión y relee una vez; solo si el fallo continúa recupera en segundo plano el servicio de este plugin cuya configuración, endpoint, worker y pertenencia del puerto de escucha ya se verificaron, y no reejecuta la navegación, la escritura o el envío que fallaron. Con `state="recovering"`, consulta el mismo trabajo según recovery.job_id y, cuando recovery_phase llegue a serving, vuelve a comprobar READY; no repitas start ni esperes succeeded. `state="recovery_required"` indica que esta vez se desactivó la recuperación; vuelve a usar recover=true solo si la instrucción del usuario lo permite. El error `pua_recovery_required` se trata según la causa de enfriamiento, pertenencia o compilación que traiga; no mates procesos por el puerto. Los dos estados de no estar listo no tienen error y, aun así, no significan READY. El tratamiento completo de cada estado está en [recuperación del canal](references/recovery.md).

Trata según el registro real los problemas de firma, capacidad, conexión, modo de desarrollador y versión, y lee [resolución de fallos](references/troubleshooting.md). Al recuperar, reutiliza la compilación y el PUA que sirvan. Vuelve a hacer build solo si la firma caducó, el binario es incompatible o la compilación ya no vale. Informa READY o NEEDS_USER_ACTION, con la capa ya verificada, lo que falta con exactitud y el paso siguiente. Si no se terminó de verificar, permanece como no listo.

## Fuentes oficiales

La [explicación de la cuenta de desarrollador](https://developer.apple.com/help/account/basics/about-your-developer-account) de Apple indica que un Personal Team puede instalar como máximo 3 apps por dispositivo y que un provisioning profile autofirmado caduca a los 7 días; entonces hay que recompilar y reinstalar. Una cuenta gratuita sirve para probar en un dispositivo personal y no permite prometer un funcionamiento permanente.

[El modo de desarrollador de Apple](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device) y la [preparación de un dispositivo físico en Appium](https://appium.github.io/appium-xcuitest-driver/latest/getting-started/device-setup/) describen los requisitos de emparejamiento, modo de desarrollador y firma. El flujo se rige por el aviso real de Xcode/iOS y por el diagnóstico de las herramientas. Este plugin no exige jailbreak.
