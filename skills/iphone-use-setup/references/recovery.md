# Recuperación del canal

Sirve cuando el servicio PUA está en marcha, pero el canal XCTest ha fallado. Si el servicio no ha arrancado en absoluto, sigue en la skill la sección «Seguir la inicialización si el servicio no está arrancado»; la firma, la confianza y la conexión están en [resolución de fallos](troubleshooting.md).

Si la navegación informa `XCTDaemonErrorDomain Code=41` / `Not authorized for performing UI testing actions`, o la app en primer plano pasa a `local.pid.0` / `pua_foreground_unavailable` y no se puede observar, no trates `status.ready=true` como prueba de que se puede operar. Es un fallo del canal PUA / XCTest y no se resuelve cambiando el selector. `pua_observe` sigue siendo de solo lectura e indica cómo recuperar READY; llama primero a `pua_ready(screenshot=false)`. Un primer plano inválido limpia la sesión y la observación antiguas y vuelve a leer una vez; si tiene éxito, devuelve `recovery.state="read_recovered"`. Solo un primer plano que sigue inválido, o un error de autorización de XCTest, entra en la recuperación del servicio, y no se reejecutan la navegación, la escritura o el envío que fallaron.

La recuperación automática solo reinicia el servicio de este plugin cuando ya se han verificado la configuración, el endpoint, la identidad del worker y el proceso que escucha de verdad en el puerto, y reutiliza la compilación válida que coincide. Con `ready=false, state="recovering"`, anota recovery.job_id, consulta el trabajo existente con los parámetros de status indicados, encuéntralo por id en el array `jobs` y revisa recovery_phase: stopping → starting → serving. Al llegar a serving, vuelve a comprobar READY y reutiliza directamente la observación nueva para ver el avance de la tarea; no repitas start. El Runner de larga duración puede seguir en running y no hay que esperar succeeded. Consulta según la fase del trabajo y el registro; no uses un bucle fijo de 15 segundos × 20 veces ni tragues un error de parseo de la respuesta. recover=false no inicia un reinicio automático, pero puede informar de un trabajo de recuperación ya existente. Este estado no trae error y MCP isError=false; aun así no significa READY ni que la tarea entera haya terminado.

`ready=false, state="recovery_required", reason="recovery_disabled"` indica que esta llamada desactivó la recuperación automática. Si la instrucción actual del usuario permite recuperar, llama otra vez según next_tool / next_arguments de recovery; si el usuario prohíbe reiniciar o pide un diagnóstico de solo lectura, informa del bloqueo del canal y conserva la restricción, sin cambiarlo a true por tu cuenta. Ese estado también es un resultado normal de diagnóstico; un rechazo real de la recuperación, el enfriamiento, la pantalla bloqueada y un fallo no clasificado siguen devolviendo error.

Cuando se devuelve `pua_recovery_required`, actúa según la causa que trae recovery: el enfriamiento dura 120 segundos; respeta retry_after_seconds y revisa el registro de la recuperación reciente. Si hay un PUA externo, la pertenencia no está clara, otro servicio ya ocupa el puerto o falta la compilación, conserva el servicio actual y ejecuta el paso manual exacto. Si de verdad hace falta reiniciar a mano, usa status para encontrar el trabajo de este plugin cuya pertenencia esté verificada, haz stop, confirma que se detuvo y solo entonces start. Un servicio externo lo reinicia su propietario; no mates procesos por el puerto ni cambies el directorio de ejecución para saltarte la comprobación. Si después del reinicio sigue el error de autorización, revisa según el aviso actual el modo de desarrollador del iPhone ya desbloqueado y «开发者 → 启用 UI 自动化»; la confianza o la confirmación de autenticación las completa el usuario.
